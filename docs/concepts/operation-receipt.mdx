title: Operation Receipt
description: "The model behind the verdict — stages, evidence, missing, and exceptions."

An **Operation Receipt** is the verdict on one payment operation. It's assembled
by the core from two inputs — the events observed, and a **template** describing
the operation's expected shape.

## Templates and stages

A template describes an operation as an ordered sequence of milestone **stages**.
Templates are per-role — each side of a payment sees only its half of the flow.
For the buyer (`x402-buyer`), the milestones are `challenge → payment →
settlement`; for the seller (`x402-seller`), `request → verification →
settlement`; for the facilitator (`x402-facilitator`), `verification →
settlement`.

Each stage's `match` is a **match-set**: any one of its events closes the stage.
This is deliberate — different client kinds witness the same milestone
differently, so the buyer's payment milestone can be closed by a signed payment
leaving an HTTP client *or* by an MCP client initiating payment for a tool call:

```yaml
- id: payment
  required: true
  match:
    - event: x402.payment.submitted  # a signed payment left the client
      role: client
    - event: x402.payment.requested  # MCP: payment for a tool call initiated
      role: client
  missing_explanation: "the challenge was observed, but no payment was initiated"
- id: settlement
  required: true
  match:
    - event: x402.payment.responded  # only a settlement that succeeded
      role: client
  missing_explanation: "the payment was submitted, but no settlement response was observed"
```

A witness may also name the `role` that has to have observed it. It is optional —
without it, any role closes the stage — and it matters wherever two roles share a
vocabulary: a resource server and a facilitator both record `x402.verify.ok` for
the same payment, so a seller's receipt would otherwise be closed by the
facilitator's witness, claiming something the run does not support.

Templates are **data, not code** — a new scenario is a new template file, never a
change to the assembler.

## The verdict

<Steps>
  <Step title="Each stage gets a state">
    `confirmed` when at least one witness from its match-set was observed;
    otherwise `not_confirmed`. A confirmed stage carries the `event_id`s of the
    witnesses behind it — the evidence.
  </Step>
  <Step title="Gaps are explained, never hidden">
    A required stage left unclosed is surfaced under `missing`, each with a
    plain-language explanation from the template's `missing_explanation`.
  </Step>
  <Step title="Faults surface as exceptions">
    An event whose type is in the template's `exceptions` (e.g.
    `x402.settle.failed`) does not close a stage — it's recorded on the
    operation as a fault.
  </Step>
  <Step title="Completeness is decided">
    `full` only when every required stage is confirmed, at least one stage
    closed, and no fault was observed. Otherwise `partial`.
  </Step>
</Steps>

## Deterministic by design

The assembler is a **pure function** — no LLM, no randomness. The same events and
template always yield the same Receipt, byte for byte. That's the evidence-chain
guarantee: a Receipt states absence rather than guessing, so it never invents a
milestone it didn't observe.

## The Receipt object

Every surface — terminal, `receipt.json`, markdown — renders the same object:

```jsonc
{
  "operation": { "template": "x402-buyer", "version": 1, "operation_id": "op-2" },
  "completeness": "partial",
  "stages": [
    { "id": "challenge", "required": true, "state": "confirmed", "events": ["evt…"] },
    { "id": "payment", "required": true, "state": "confirmed", "events": ["evt…"] },
    { "id": "settlement", "required": true, "state": "not_confirmed", "events": [] }
  ],
  "missing": [
    { "stage": "settlement",
      "expected_events": ["x402.payment.responded"],
      "why": "the payment was submitted, but no settlement response was observed" }
  ],
  "exceptions": [],
  "events": [ /* every discovered event, for provenance */ ]
}
```

For an agent, `completeness: "partial"` plus `missing: [settlement]` is a
machine-readable basis to stop a chain of spending.
